# 모바일 PowerShell 기록 스크롤

2026-09-29, 사용자가 Android 삼성 인터넷에서 PowerShell의 이전 출력이 손가락으로 스크롤되지 않는다고 보고했다. 키보드와 글자 크기 조절 뒤에 이어진 별도 입력 동작 문제다.

## 재현과 원인

설치된 xterm 6의 `Viewport`는 실제 DOM의 세로 스크롤 대신 가상 스크롤 상태를 사용한다. 내부 `SmoothScrollableElement`에는 마우스 휠과 마우스 이벤트가 연결돼 있으나, 터미널 내용에 손가락 드래그를 연결하는 경로가 없다. 기존 `.xterm-screen {touch-action:pan-y}`만으로는 터미널 기록이 이동하지 않았다.

실제 Chrome CDP 터치 입력으로 재현했다. 일반 버퍼에 기록 100줄을 넣고 손가락을 아래로 움직여도 `baseY=viewportY=93`과 표시 줄이 그대로였다. 직접 `scrollLines`를 호출하거나 합성 휠을 보내는 방식으로 재현을 대체하지 않았다. 실사용 PowerShell에는 별도 읽기 전용 메타데이터 확인 당시 이전 출력 44줄이 있었으며 기록 생략은 없었다. 사용자의 출력 내용이나 입력은 기록하지 않았다.

별도로 기존 화면 복원은 아래쪽 끝까지의 거리를 유지했다. 과거 `LINE_010`을 읽는 중 5줄의 새 출력이 오면 화면이 `LINE_015`로 밀리는 것을 격리 시험에서 확인했다.

## 수정

일반 출력 기록이 있는 터미널에서 한 손가락 세로 이동을 로컬 스크롤에 연결했다. 작은 움직임과 탭은 그대로 두며, 여러 손가락 입력은 브라우저 확대 동작에 맡긴다. 스크롤은 제어권이나 셸 입력과 무관하므로 보기 전용에서도 사용할 수 있다. 셸로 방향키나 마우스 휠 명령을 보내지 않는다. 리스너는 패널 정리 시 해제한다.

화면 크기가 같고 읽던 내용이 같은 기록 위치에 남아 있다면 새 출력이 와도 그 위치를 유지한다. 기록이 생략되거나 화면 크기·내용이 바뀌어 같은 위치를 유지할 수 없으면 기존의 아래쪽 끝까지 거리 보존을 사용한다. 맨 아래에 있을 때는 새 출력을 따라간다.

## 검증 상태

기존 모바일 키보드·표시 회귀 검사 **5/5 통과, 실패·생략 0, 18.858초**. 입력 동기화 중 포커스 유지, 잘못된 제어권 입력 차단, 글자 크기·넓게 보기·설정 유지와 좁은 화면 배치를 확인했으며 페이지 JavaScript 오류가 없었다.

터치 회귀 **4/4**, 기존 터미널 검사 **18/18**, TypeScript 검사와 웹 빌드가 통과했다. 소스 독립 검토에서도 배포를 막는 결함을 찾지 못했다.

- 보기 전용 상태에서 실제 Chrome CDP 손가락 스와이프로 `viewportY 93 → 89 → 93`의 양방향 이동을 확인했다. 셸 입력은 발생하지 않았다.
- 과거 `history-089`를 읽던 상태에서 새 출력과 8회 화면 갱신 후에도 같은 줄·위치가 유지됐다.
- 입력 포커스가 있는 상태에서도 blur와 readOnly 변경은 각각 0회였으며, 같은 입력란으로 이후 글자를 한 번만 전송했다.
- 두 손가락 핀치 중 터치 기본 동작을 취소하지 않았고 실제 `visualViewport.scale`이 `1 → 3.603`으로 증가했다. 전체 화면 대체 버퍼에서 스와이프를 셸 입력으로 바꾸지 않았으며, dispose 후에는 리스너가 작동하지 않았다.

근거: `test-results/mobile-scroll/result.md`, 측정 JSON 4개, `ui-regression.txt`. 위 자동 검사는 Windows Chrome의 터치 입력 시험이며, 실제 삼성 인터넷과 휴대폰 OS 키보드 검증과 구분한다. 웹 수정 배포 후 사용자가 **Android 삼성 인터넷에서 “스크롤 잘 됨”**으로 정상 동작을 확인했다. 이 사용자 확인이 모든 기기·키보드·프로그램 조합의 검증을 의미하지는 않는다.
