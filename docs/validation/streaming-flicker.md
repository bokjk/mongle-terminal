# 답변 출력 중 화면 깜박임 후속 수정 (2026-09-29)

## 재현과 원인

앞선 GJC 수정은 DEC 2026 출력 완료를 기다리고 xterm의 예약된 화면 갱신을 보류했다. 그러나 몽글의 완전한 화면 스냅샷 적용은 매번 `terminal.reset()`을 호출한다. xterm 6의 BufferSet.reset은 onBufferActivate 이벤트를 발생시키고, RenderService는 이 이벤트에서 DOM renderer.clear를 즉시 호출한다. 이 호출은 synchronizedOutput을 확인하지 않으며 모든 행의 DOM을 비운다. 선택 변경·포커스도 renderer.renderRows를 직접 호출하는 별도 경로가 있다.

기존 검사는 xterm onRender 이벤트에서만 내용을 관찰하여 직접 DOM을 지우는 순간을 놓쳤다. 이번 검사는 requestAnimationFrame마다 실제 `.xterm-rows` 텍스트를 수집한다. 수정 전 일반 기록과 대체 화면의 연속 출력 두 시나리오 모두 실패했고 각 21개의 빈/불완전한 화면이 관찰됐다.

## 수정

reset **전에** xterm renderer의 clear·renderRows·resize·selection 진입점을 잠시 보류한다. 새 화면 파싱과 입력 모드·스크롤·선택 복원을 마치면 같은 JavaScript 작업 안에서 완성된 화면을 반영한다. 그동안 이전의 실제 텍스트 DOM과 입력 요소를 유지하며 이미지나 가림막으로 덮지 않는다. 오류·종료 때는 원래 메서드를 복구하고 폐기한 renderer를 다시 그리지 않는다. 내부 API 접근은 pinned-xterm.ts에 한정한다.

이는 원격 접속용 전체 스냅샷 프로토콜을 유지하는 수정이다. 매번 스냅샷을 파싱하는 비용까지 제거한 증분 전송 구현은 아니다.

## 검증 범위

- 변경 전 실패한 실제 Chrome RAF 검사 2/2 통과: 24줄 기록을 가진 일반 화면 및 대체 화면에서 각각 3개 연속 프레임을 느리게 적용하며 빈/중간 화면이 없는지 확인.
- 전체 터미널 검사 32개 통과, 실패 0, 선택적 GJC 재생 1개 생략 (10.96초). 화면 안의 선택 강조가 즉시 복원되는지도 확인했다.
- 타입 검사·빌드 통과. 기존 웹 번들 크기 안내 외 오류 없음.
- 실제 Electron/PowerShell 복사·붙여넣기 E2E 통과 (4.53초): 자동 복사, 선택 있는/없는 Ctrl+C, Ctrl+V, 우클릭 붙여넣기 및 여러 줄 취소 유지.
- 이번 재현은 답변 출력과 같은 연속 갱신·느린 파싱 조건을 사용했다. 유료 AI 요청을 보내 실제 Claude 답변을 생성한 검증은 아니다.
- 수정본 적용 후 사용자가 실제 사용에서 "잘되네"라고 정상 동작을 확인했다. 이는 위 자동 검사와 별도의 사용자 확인이다.

## 현재 앱 적용

최종 웹 코드의 파일 해시를 확인하고 `release/win-unpacked`에 적용했다. GUI는 33348에서 30860으로 다시 열었고, 호스트 PID 39240과 bootId는 변경하지 않았다. 최종 패키지의 실제 클립보드 E2E도 통과했다 (5.04초). 기록: `test-results/streaming-rollout/deployment.json`.
