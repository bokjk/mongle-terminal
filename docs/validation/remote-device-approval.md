# 원격 기기 승인

2026-10-09~10, Windows x64, 0.3.19 배포 준비. 이미 승인된 기기가 같은 원격 주소로 들어온 새 기기의 연결을 대신 승인할 수 있게 했다. 배포 검사는 [0.3.19 배포 검증](public-release-0.3.19.md)에 기록한다.

## 배경

컴퓨터 선택 메뉴에 멀리 있는 PC를 등록하려면 접속받을 PC의 화면에서 연결 코드를 만들고 승인해야 했다. 원격 기기의 `pairing.*` 요청은 게이트웨이에서 모두 `FORBIDDEN`이었고 코드는 3분 안에 써야 해서, 서로 떨어진 두 PC는 원격 데스크톱 없이 등록할 수 없었다. 30일이 지나 만료된 기기를 다시 승인할 때도 같은 제약이 있었다. 사용자는 Tailscale 자동 찾기나 사용 중 자동 연장보다 "승인된 휴대폰으로 대신 승인하기"를 먼저 선택했다.

## 변경

- 게이트웨이: 승인된 원격 WebSocket 세션의 `pairing.create`·`pairing.list`·`pairing.approve`·`pairing.reject`를 게이트웨이에서 직접 처리하고 core로 전달하지 않는다. 세션 origin과 같은 요청만 조회·결정한다. 승인 관련 요청은 기기당 분당 60회, 코드 생성은 분당 10회로 제한한다. `remote.*`·`devices.*`·`pairing.status`·`host.*`는 계속 PC 전용이다.
- 인증 저장소: `pairings`·`sessions`에 `approved_by` 열을 두고 이전 DB에는 시작할 때 추가한다. 원격 승인이면 승인한 기기 이름을 기록하고 claim 때 세션으로 옮겨 `devices.list`의 `approvedBy`로 제공한다.
- 호스트 상태: `pairing.remote-approve` capability를 알린다. 이를 알리지 않는 이전 호스트에 데스크톱 앱이 원격으로 연결하면 예전 안내만 표시하고 승인 목록을 조회하지 않는다.
- 설정 화면: 연결된 기기의 원격 연결 탭에 **새 기기 연결**(코드 만들기·복사, 남은 시간, 승인 대기 목록, 승인·거절)과 **이 기기의 연결**을 표시한다. 새 기기 연결 섹션은 PC 화면과 공유하며 승인하면 명령 실행 권한이 생긴다고 안내한다. 코드와 요청의 남은 시간을 1초마다 갱신하고 만료된 코드는 감춘다. 700px 이하에서는 거절·승인 버튼을 같은 폭으로 나란히 두고 승인을 오른쪽에 둔다. PC의 연결한 기기 목록에는 "○○에서 승인"을 표시한다. 승인 목록 조회가 연속으로 실패하면 한 번만 알린다.
- 연결 화면: "설정 → 원격 접속" 안내를 실제 탭 이름인 "설정 → 원격 연결"로 고치고, 이미 연결된 기기에서도 코드를 만들고 승인할 수 있다고 안내한다.

## 디자인 참고 (Mobbin)

2026-10-09에 Aside 브라우저로 Mobbin에서 로그인 없이 볼 수 있는 탐색 페이지를 확인했다.

- Connecting & Linking 흐름의 Trust Wallet "Adding a DApp connection": 설정 → 연결 관리 → 요청 확인 화면 → 연결 목록 순서다. 요청 확인 화면은 요청자 이름·도메인과 허용되는 권한을 보여 주고 왼쪽에 Cancel, 오른쪽에 강조한 Connect 버튼을 둔다. 적용: 승인 목록에 요청 기기 이름과 승인 시 생기는 명령 실행 권한을 안내하고, 휴대폰에서는 거절·승인 두 버튼을 나란히 두며 승인을 오른쪽에 강조했다.
- Logging In 흐름의 Plata Card "Logging in": 인증 코드 화면에 "Resend in 4 sec"처럼 남은 시간을 보여 준다. 적용: 3분짜리 연결 코드와 승인 요청에 만료 시각 대신 남은 시간을 표시했다.
- 로그인이 필요한 Signal·WhatsApp 등의 기기 연결 화면은 확인하지 못했다.

## 1차 실제 앱 조작 (2026-10-10, 부분 검증)

아스트라(`gpt-6-astra`)가 실제 개발 Electron 앱을 TEMP 아래 별도 `MONGLE_DATA_DIR`로 실행해 조작했다. PC의 **설정 → 원격 연결 → 접속 주소 직접 설정**에서 가짜 시험 주소를 저장하고 **연결 코드 만들기** 버튼 활성화, 코드 생성, 남은 시간의 `2:48 → 2:15` 감소를 확인했다. 초기 `3:00` 순간은 확인하지 않았다. **원격 접속 켜기**는 누르지 않았으며 실제 Tailscale Serve를 변경하지 않았다.

Aside CLI/REPL의 공개 안내와 Aside 자체 에이전트 조사에서 독립 쿠키 컨텍스트 생성 경로를 확보하지 못했다. REPL의 `page.context()`도 지원되지 않았다. 사용자 브라우저 쿠키를 삭제하거나 인증을 우회하지 않고 브라우저 인증 시험을 중단했다. 따라서 PC에서 휴대폰 역할 브라우저를 처음 승인하는 단계부터 미수행이며, 휴대폰의 새 기기 승인·거절, 실제 새 기기의 터미널 연결, PC 목록의 승인 기기 표시, 390px에서의 버튼 배치·가로 넘침은 이번 실앱 시험으로 확인하지 않았다. 위 자동 검사 결과와 구분한다.

시험 호스트는 설정 화면의 정상 종료 절차로 종료했고 시험용 Node·OwnerPipe가 사라진 것을 확인했다. 개발 Electron 프로세스는 남아 일반 종료 요청도 실패했으므로, 호스트 종료 후 식별한 시험 PID만 강제로 정리했다. 마지막 확인에서 시험 프로세스 잔존은 0개였고 기존 사용자 주요 프로세스 7개는 모두 유지됐다. 따라서 앱 전체의 정상 종료를 통과 처리하지 않는다. 이번 승인 기능 변경이 원인인 결함으로 확정한 사항은 없다.

스크린샷 3장과 `observations.json`, `cleanup-result.json` 등 시험 기록은 커밋하지 않는 `test-results/remote-approval-live/`에 둔다. 스크린샷의 연결 코드·PC 이름은 가리고 사용자 경로는 잘라냈다. 이 부분 검증만으로 기능의 실제 기기 간 승인 흐름을 통과 처리하지 않는다.

### 1차 종료 기록의 코드 확인

`apps/desktop/main.ts`에서 설정의 `host.shutdown`은 호스트를 멈춘 뒤 앱을 오프라인 상태로 두며 `app.quit()`을 호출하지 않는다. Windows 창 닫기도 트레이가 있으면 창을 숨긴다. 앱 메뉴·트레이의 **앱 종료 · 터미널 유지**가 `app.quit()`을 호출하고, **완전 종료…**는 호스트 저장·종료 확인 뒤 앱을 종료한다. 따라서 1차 시험에서 호스트 종료 후 Electron이 남은 사실만으로 앱 종료 결함이라고 판단할 수 없다. 당시 `Ctrl+Q`와 일반 프로세스 종료 요청은 실제 앱 종료 메뉴를 누른 검증이 아니었다. 재시험에서는 정식 메뉴로 앱까지 종료되는지 별도로 확인한다.

## 2차 실제 앱·브라우저 조작 (2026-10-10)

사용자가 이번 검증에 한해 BrowserOS neo를 임시 허용했다. 아스트라(`gpt-6-astra`)가 BrowserOS를 휴대폰, Aside를 새 기기로 나눠 각 브라우저의 새 시험 탭만 조작했다. 새 TEMP 프로필로 개발 Electron과 실제 호스트·게이트웨이를 실행했다. 실제 Tailscale Serve는 변경하지 않았다.

Aside에는 기존 `127.0.0.1` 인증 쿠키가 있어 이를 보존하려고 별도 시험 호스트 `mongle-pr63-test.localhost`를 사용한다. 커밋하지 않는 `test-results/remote-approval-two-browsers/loopback-proxy.mjs`는 루프백에만 바인딩하고 이 주소의 HTTP·WebSocket을 격리 게이트웨이로 전달한다. 고정된 Host·Origin과 WebSocket 접속 주소만 변환하며 제품 인증·CSRF 검사를 바꾸거나 우회하지 않는다. 정상 Host의 상태 확인은 200, 다른 Host·Origin은 403임을 확인했다. 기기 승인·거절은 실제 앱 UI로 수행해야 하며, 이 중계 시험을 실제 Tailscale이나 서로 다른 원격 origin의 보안 격리 시험으로 해석하지 않는다.

- PC에서 휴대폰 역할 BrowserOS의 연결 요청을 승인한 뒤 실제 작업 공간에 연결되는 것을 확인했다.
- 휴대폰의 **새 기기 연결**과 **이 기기 연결 해제**(본인 로그아웃)가 보이고, PC 전용 원격 켜기·끄기와 다른 기기 접속 권한 해제는 없는 것을 확인했다. 휴대폰이 생성한 코드의 남은 시간은 `2:59 → 2:32`로 감소했다.
- 휴대폰 역할 BrowserOS의 화면을 390px로 설정해 실제 승인 대기 요청을 확인했다. 거절·승인 버튼은 각각 156.5×44px로 같은 높이에 나란히 배치됐고 승인이 오른쪽이었다. 문서 너비도 390px로 가로 넘침이 없었다. 실물 휴대폰 시험은 아니다.
- 휴대폰이 만든 코드로 Aside에서 요청하고 휴대폰에서 승인했다. 새 기기가 실제로 연결돼 시험 PowerShell 터미널 탭과 **1개 실행 중** 표시를 확인했다. PC 기기 목록에는 **PR63-Phone-Neo에서 승인**이 표시됐다.
- 새 기기의 본인 연결을 해제하고 다시 요청한 뒤 휴대폰에서 거절했다. Aside에 거절 안내·오프라인 상태가 표시되고 터미널 패널이 없는 것을 확인했으며, 연결 코드를 가린 DOM 기록으로 남겼다. 이후 휴대폰에서 새 코드를 만들 때 **3:00 남음** 시작 표시도 실제 DOM에서 확인했다.
- Aside 캡처는 기본 대기와 5초 재시도에서 시간 초과가 났다. 따라서 새 기기의 실제 터미널 탭·실행 상태·거절 결과는 DOM으로 확인한 범위이며 터미널 픽셀 표시를 확인한 것으로 표현하지 않는다. 390px 승인 대기 화면과 PC 승인 출처는 스크린샷을 직접 열어 확인했다.
- 두 시험 기기는 본인 로그아웃으로 연결을 해제하고 시험 탭만 닫았다. BrowserOS의 화면 크기 설정을 복원했다. Aside의 기존 `127.0.0.1` 쿠키는 보존했으며 시험 호스트와 BrowserOS의 시험 인증 쿠키는 제거된 상태를 확인했다. 쿠키 값은 출력하지 않았다.
- 호스트·시험 셸은 설정 UI로 정상 종료했다. 숨김 제목 표시줄의 개발 Electron에서 앱 종료 메뉴에 안전하게 접근하지 못했으므로, 호스트 종료 후 실행 경로와 PID로 식별한 시험 Electron만 강제 정리했다. 중계·쿠키 확인용 시험 서버도 종료했다. 마지막 확인에서 시험 프로세스 잔존 0개, 기존 주요 프로세스 7/7 유지였다. **앱 전체 정상 종료는 여전히 미검증**이며, 이번 승인 기능에 의한 제품 회귀로 확정한 문제는 없다.

스크린샷·DOM·수행 및 종료 기록은 `test-results/remote-approval-two-browsers/`에만 보관하고 커밋하지 않는다. 연결 코드·PC 이름·사용자 경로는 가리거나 제외했다. 브라우저 승인·거절 흐름은 이번에 확인했지만, 실제 Tailscale·실물 휴대폰·두 PC 간 등록은 아래 미검증 범위로 남긴다.

## 독립 코드 검토와 수정 (2026-10-10)

PR #63을 정식 PR로 바꿔 GitHub의 Codex 자동 검토를 받고, 아스트라(`gpt-6-astra`)에게 기능 커밋 `9fa4d2f`의 읽기 전용 독립 검토를 맡겼다. P2 지적 2건을 모두 반영했다.

- 다른 기기의 코드 무효화(GitHub Codex 검토): 코드를 만들 때 `DELETE FROM codes`로 모든 코드를 지워, 휴대폰 B가 코드를 만들면 PC나 휴대폰 A가 아직 보여 주는 코드가 말없이 무효가 됐다. 이제 `codes.issuer`에 발급자를 기록하고 PC와 각 기기가 코드를 하나씩 유지한다. 새 코드는 같은 발급자의 이전 코드만 대체한다. 실패한 추측은 여전히 살아 있는 모든 코드에 더해지므로 5회 실패 한도는 약해지지 않는다. 이전 DB에는 시작할 때 열을 추가하고, 열이 없던 시절의 코드는 PC 코드로 취급한다.
- 시계 차이로 코드·요청 숨김(아스트라 검토): 화면이 호스트가 정한 만료 시각을 기기 시계와 그대로 비교해, 휴대폰 시계가 PC보다 4분 빠르면 방금 만든 코드와 유효한 승인 요청을 만료로 보고 감췄다. 이제 `pairing.create`·`pairing.list` 응답에 호스트 시각(`serverTime`)을 담고, 화면은 요청 왕복의 중간 시점을 기준으로 시계 차이를 보정해 남은 시간과 만료를 계산한다. 새 추정치가 현재 값과 왕복 시간(최소 1초)보다 크게 다를 때만 바꿔, 남은 시간이 튀지 않고 지연이 고르지 않아도 정확한 값을 덮어쓰지 않게 했다. 이 값을 보내지 않는 이전 호스트에서는 예전처럼 기기 시계를 쓴다. 최종 만료 판정은 계속 호스트가 한다.
- 시험: 보안 25/25(발급자별 코드 유지·대체와 모든 코드 잠금 시험 추가, 이전 DB 시험에 코드 발급자 열 추가와 기존 PC 코드 유지 확인, 게이트웨이 시험에 PC 코드 유지와 응답 시각 확인), 설정 화면 3/3(호스트 시계가 4분 느린 경우 새 코드와 요청의 남은 시간 표시 확인), 타입 검사 통과. 수정 전 코드로 잠시 되돌리면 새 시험이 실패하는 것도 확인했다(화면은 코드가 나타나지 않아 시간 초과, 저장소는 2건 실패).
- 재검토(아스트라, `0c0f709`): P2 2건 해결을 확인했고 새 P0~P2는 없었다. P3 1건, 보내기·받기 지연이 크게 다르면 보정값이 왕복 시간의 절반까지 틀어져 아직 유효한 요청을 몇 초 일찍 숨길 수 있다는 지적을 반영했다. 위처럼 왕복 시간보다 큰 차이만 반영하므로 지연 비대칭만으로는 정확한 값을 바꾸지 못한다. 계산을 `apps/web/src/host-clock.ts`로 옮기고 `tests/ui/host-clock.test.ts` 1/1로 빠른 응답의 4분 차이 보정, 1초 이하 변동 무시, 6초 비대칭 지연 거부, 느린 응답으로 큰 차이를 보정한 뒤 빠른 응답으로 정밀화, 잘못된 값 무시를 확인했다.
- 아스트라 검토는 그 밖에 PC 전용 호출 차단, origin 제한, 만료·처리된 요청·없는 ID 처리, 기기별 횟수 제한, 열 추가의 재시작 안전성, 이전 호스트에서의 숨김에서 결함을 찾지 못했다고 보고했다. 정적 검토이며 시계 차이 재현은 위 화면 시험으로 대신했다.

## 확인하지 않은 범위

- 새 기기 터미널의 픽셀 표시(Aside 캡처 시간 초과). 실제 탭·실행 상태와 승인·거절 흐름은 2차 시험의 DOM으로 확인했다.
- 개발 Electron의 정식 앱 종료 메뉴를 통한 전체 정상 종료. 호스트·셸 정상 종료와 시험 프로세스 정리는 확인했다.
- 실제 Tailscale HTTPS, 실물 휴대폰, 두 PC 사이의 컴퓨터 추가와 휴대폰 승인 전체 흐름. 게이트웨이 시험은 Serve가 전달하는 Host·Origin 헤더를 모사했다.
- 이 PC에서의 패키지·NSIS 설치본 수동 조작. 원격 CI의 설치·복원 검사는 위에서 별도로 확인했다.
- 승인한 기기를 해제해도 그 기기가 승인한 기기는 해제하지 않는다. 설계상 결정이며 이유는 [보안 설계](../03-security-and-remote.md#승인된-기기의-대리-승인--2026-10-09-추가)에 기록했다.
