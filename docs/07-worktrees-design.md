# 워크트리 기능 설계안

작성일: 2026-10-01 · 상태: 미배포 개발 구현의 설계 기준 · 대상: 몽글터미널 0.3.6 코드 기준

**프로젝트 안에 워크트리를 등록하고, 이름을 누르면 연결된 터미널을 찾거나 새로 연다.** 여러 워크트리의 터미널은 같은 프로젝트 화면의 탭·분할에 함께 둔다. 워크트리 생성과 터미널 실행은 별도 동작으로 관리한다.

이 문서는 합의한 사용 흐름, 코드 변경 범위, 구현 순서와 완료 기준을 보존한다. 실제 구현·검증 상태와 미확인 범위는 [워크트리 검증 기록](validation/worktrees.md)을 따른다. 공개 배포 완료를 뜻하지 않는다. 이전 이미지 시안보다 이 문서의 동작 규칙을 우선한다.

## 확정 요구와 제안 기본값

| 구분 | 내용 |
|---|---|
| 사용자 요구 | 생성 버튼은 `+ 워크트리`로 표시한다. |
| 사용자 요구 | 생성할 때 터미널도 열지 선택할 수 있다. |
| 사용자 요구 | 터미널 없이 만든 워크트리도 나중에 이름을 누르면 터미널을 만든다. 이미 있으면 그 터미널을 포커스한다. |
| 사용자 요구 | 터미널에 워크트리 이름을 표시하고, 프로젝트 안에서 여러 작업을 함께 사용한다. |
| 제안 기본값 | `생성 후 터미널 열기`를 처음에는 켠다. 별도의 확인 팝업 대신 생성 폼의 체크박스로 선택한다. |
| 제안 기본값 | 새 터미널은 현재 패널의 새 탭으로 연다. 사용자가 분할 버튼이나 드래그로 배치한다. |
| 제안 기본값 | 마지막으로 성공한 기준 브랜치를 프로젝트별로 기억한다. 최초에는 등록한 작업 폴더의 현재 브랜치를 제안하고 항상 화면에 표시한다. `main`을 고정하지 않는다. |
| 제안 범위 | 첫 구현은 선택한 Windows 호스트의 로컬 Git 저장소를 대상으로 한다. 일반 그룹·기존 터미널 사용도 계속 지원한다. |

## 사용자가 처음 시작하는 흐름

1. 사이드바의 **프로젝트 열기**를 누른다. 이 PC에서는 폴더 선택 창으로 기존 프로젝트를 고른다. 원격에서는 선택한 호스트 이름을 표시하고 그 컴퓨터의 폴더 경로를 입력받는다.
2. 호스트가 Git 저장소와 기존 워크트리를 확인한다. 새 프로젝트는 사이드바에 등록하고 선택한 폴더의 터미널 하나를 연다. 이미 등록된 저장소라면 기존 프로젝트로 이동하며, 터미널도 재사용한다.
3. 프로젝트 아래 **원래 작업**, 발견한 워크트리, **+ 워크트리**를 보여준다. 원래 작업은 실제 기본 작업 폴더이며 브랜치 이름을 함께 표시한다.
4. **+ 워크트리**에서 이름·기준 브랜치·터미널 열기 여부를 확인하고 생성한다. Git 명령이나 별도 폴더 복사를 사용자가 직접 할 필요가 없게 한다.

Git 저장소가 아닌 폴더에는 일반 그룹으로 여는 선택지를 제공한다. 자동으로 `git init`하지 않는다. Git 미설치, 첫 커밋이 없는 저장소, 지원하지 않는 경로는 원인을 해당 화면에 표시하며 기존 터미널 사용을 막지 않는다.

기존 그룹은 메뉴의 **프로젝트 연결**로 저장소를 연결한다. 그룹의 이름·배치·실행 중인 터미널은 유지한다. 같은 저장소를 여러 프로젝트로 중복 등록하는 대신 기존 연결을 찾아 안내한다.

## 화면과 조작

### 사이드바와 터미널

```text
프로젝트 열기

▾ 몽글터미널                        ⋯
    원래 작업           [터미널 1]
    dev
    로그인 수정         [터미널 2]
    feat/login
    디자인 변경         터미널 없음
    feat/design
    + 워크트리

오른쪽의 한 패널 예시
[원래 작업 · PowerShell] [로그인 수정 · 개발 서버] [로그인 수정 · 테스트] [+]
```

프로젝트 제목에는 펼치기와 메뉴만 둔다. 워크트리를 만드는 `+`를 제목 옆에 중복 배치하지 않는다. 프로젝트 제목을 누르면 그 프로젝트의 기존 화면으로 이동하고, 펼치기 화살표는 목록만 접거나 편다.

워크트리 행의 숫자는 **이 프로젝트에 열려 있는 해당 워크트리의 터미널 수**다. 종료된 출력이 남아 있는 탭도 포함한다. 숫자 버튼을 누르면 터미널 제목·상태 목록을 열어 직접 고를 수 있게 한다. 작업 수나 변경 파일 수와 혼동하지 않도록 터미널 아이콘과 접근성 이름을 붙인다.

터미널의 워크트리 표시는 사용자가 바꾸는 터미널 제목과 분리한다. 예를 들어 `로그인 수정 · 개발 서버`에서 앞부분은 연결된 워크트리 이름, 뒷부분은 터미널 제목이다. 워크트리 이름을 바꿔도 Git 브랜치나 폴더 이름을 자동으로 바꾸지 않는다.

| 조작 또는 상태 | 동작 |
|---|---|
| 워크트리 이름 클릭, 연결된 터미널 없음 | 워크트리 루트에서 기본 셸을 새 탭으로 하나 열고 포커스한다. 빈 화면이면 첫 패널을 만든다. |
| 연결된 터미널 있음 | 이 기기에서 마지막으로 선택한 터미널을 찾는다. 없으면 실행 중인 터미널을 우선하고, 모두 종료 상태면 기존 출력 탭을 보여준다. |
| 다른 탭 뒤에 있거나 다른 패널에 있음 | 해당 탭을 선택하고 패널 위치를 드러낸다. 기존 분할 비율과 다른 탭의 실행 상태를 유지한다. 최대화 중이면 대상 터미널로 전환한다. |
| 터미널 탭의 `+` 또는 분할 버튼 | 선택한 터미널에 연결된 워크트리의 터미널을 추가한다. 새 워크트리는 만들지 않는다. 생성 폼에 대상 워크트리를 표시한다. |
| 터미널을 모두 닫은 뒤 워크트리 클릭 | 폴더는 남아 있으므로 다시 새 터미널 하나를 연다. |
| 터미널 프로세스만 종료되어 출력 탭은 남음 | 기존 출력을 먼저 보여주고 `새 셸로 다시 열기`를 제공한다. 클릭만으로 기록을 지우거나 이전 명령을 실행하지 않는다. |
| 다른 그룹으로 터미널 이동 | 워크트리 연결·실행 경로·프로세스는 유지한다. 원래 프로젝트의 숫자에서는 제외하고, 그 프로젝트에 터미널이 없으면 다음 클릭 때 새로 연다. |
| 원격 호스트 연결 끊김 | 저장된 목록·출력을 표시할 수 있지만 생성·삭제는 비활성화한다. 다른 컴퓨터에서 대신 만들지 않는다. |

최근 선택은 기기별 상태다. 다른 PC에서 클릭했다고 이 PC의 활성 탭을 바꾸지 않는다. 사이드바 이동만으로 다른 기기의 터미널 제어권을 가져오지 않으며, 실제 입력 제어는 기존 제어권 흐름을 따른다.

워크트리 목록과 브랜치는 프로젝트 연결·선택, 앱을 다시 활성화할 때, Git 생성·삭제 완료 후에 갱신한다. 메뉴에 `목록 새로고침`도 둔다. 갱신 요청은 합치고, 실패하면 마지막 확인 정보임을 표시한다. 일반 그룹의 워크트리 연결 없는 터미널은 기존 탭·분할 동작을 유지한다.

키보드는 행을 Tab으로 탐색하고 Enter로 연다. 메뉴·숫자 버튼에는 별도 접근성 이름을 준다. 모바일에서는 같은 규칙으로 대상 터미널을 선택하고 사이드바를 닫는다. 터치 영역은 최소 44px을 확보한다.

### 워크트리 생성 폼

| 항목 | 표시와 기본값 |
|---|---|
| 제목 | 워크트리 만들기 |
| 프로젝트와 실행 위치 | 예: `몽글터미널 · 이 PC`. 다른 호스트를 선택했다면 그 호스트 이름을 표시한다. |
| 워크트리 이름 | 사용자가 입력한다. 한글 허용. 프로젝트 안에서 알아볼 수 있는 이름을 사용한다. |
| 기준 브랜치 | 항상 표시한다. 기존 선택을 기억하되 없어진 브랜치는 다시 고르게 한다. detached HEAD면 커밋과 상태를 명확히 표시한다. |
| 새 브랜치와 생성 위치 | 자동 제안값을 요약으로 보여준다. `고급 설정`에서 수정한다. Git 이름 규칙과 중복을 실제로 검사한다. |
| 생성 후 터미널 열기 | 기본 선택. 해제하면 안내 문구 `나중에 워크트리 이름을 누르면 터미널이 열립니다.`를 표시한다. |
| 기본 버튼 | 선택 시 `만들고 터미널 열기`, 해제 시 `워크트리 만들기` |

기본 생성 방식은 **새 브랜치 만들기**다. 기존 브랜치 연결은 고급 설정에서 선택하며 다른 워크트리에서 사용 중인 브랜치는 이유를 표시하고 선택을 막는다. 생성 중에는 버튼을 잠그고 `워크트리 만드는 중…` 상태를 표시한다.

선택한 기준 커밋으로 새 작업 폴더를 만든다. 원래 폴더의 커밋하지 않은 변경이나 `.env`, 설치된 의존성을 자동으로 복사하지 않는다. 폼에는 `기준 브랜치의 커밋으로 시작합니다`를 짧게 안내한다.

터미널 열기를 끄면 현재 탭·분할·포커스는 그대로 두고 사이드바에 항목만 추가한다. 켠 경우에도 생성하는 동안 사용자가 다른 프로젝트나 호스트로 이동했다면 완료 알림만 보여주고 화면을 강제로 되돌리지 않는다.

화면에서는 프로젝트 아래 묶지만 **실제 폴더는 원본 저장소 밖**에 만든다. 기본 제안은 `<원본 폴더의 부모>/<프로젝트명>.worktrees/<안전한 이름>-<짧은 ID>`다. 원본 내부·Git 메타데이터 내부·앱 데이터 폴더·다른 워크트리 내부는 생성 대상으로 허용하지 않는다. 권한이나 경로 문제가 있으면 다른 위치를 선택할 수 있게 한다.

### 현재 폴더와 워크트리 연결

워크트리 표시는 터미널이 연결된 작업의 이름이다. 셸에서 `cd`했다고 연결이나 기존 실행 명령을 자동 변경하지 않는다. 현재 경로가 연결된 워크트리 밖이면 `다른 폴더에서 작업 중`을 표시한다. 경로 보고가 없는 셸은 시작 폴더라는 사실을 표시한다.

새 탭의 기본 위치는 연결된 워크트리의 루트다. 파일·Git 보기는 기존처럼 선택한 터미널의 보고된 현재 경로를 우선하며, 보고가 없으면 시작 경로를 사용한다. 사이드바에는 마지막으로 확인한 실제 브랜치를 표시하고 갱신 실패·detached 상태를 구분한다.

## 데이터와 코드 구조

현재 [프로토콜](../packages/protocol/index.ts)은 `Group`, `TerminalInfo`, `LayoutNode`를 갖고 있다. **프로젝트는 저장소와 연결된 기존 Group으로 구현하고 LayoutNode는 유지한다.** 워크트리마다 그룹이나 탭 컨테이너를 새로 만드는 구조는 필요하지 않다.

| 데이터 | 역할과 필요한 필드 |
|---|---|
| Repository | 호스트 안에서 안정적인 `id`, 정규화한 Git 공통 메타데이터 경로, 기본 작업 폴더, 기본 기준 브랜치, 생성 위치 설정 |
| Worktree | 안정적인 `id`, `repositoryId`, 표시 이름, 정규화한 실제 경로, 원래 작업 여부, 앱 생성 여부, 확인한 브랜치·HEAD·잠금·존재 상태 |
| Group | 기존 필드에 선택적 `repositoryId` 추가. 연결 없는 그룹도 그대로 유효 |
| TerminalInfo | 선택적 `worktreeId` 추가. `groupId`, `cwd`, `currentCwd`, PID·generation과 별도로 유지 |
| Operation | 생성·삭제 요청 ID, 작업 ID, 저장소·워크트리 대상, 진행 단계, 결과 또는 복구가 필요한 상태 |

경로나 브랜치 이름만으로 식별하지 않는다. 경로는 `realpath` 및 Windows 경로 규칙으로 확인하고 Git 공통 메타데이터 위치로 같은 저장소를 판별한다. 표시 이름 변경은 식별자에 영향을 주지 않는다. Git에서 밖으로 이동·삭제한 경우 조용히 새 폴더를 만들지 않고 다시 확인할 상태로 남긴다.

기존 터미널은 프로젝트를 연결할 때 시작 폴더가 해당 워크트리에 속함을 확인한 경우에만 연결 메타데이터를 붙인다. 기존 프로세스를 재시작하거나 `cd`를 입력하지 않는다. 현재 cwd만 보고 시작한 작업의 소속을 추측하지 않는다.

| 코드 영역 | 변경 계획 |
|---|---|

### 호스트 요청과 중복 방지

새 요청은 `projects.inspect/attach`, `worktrees.refresh/create/open/remove`, `worktrees.operation`으로 나눈다. 명칭은 구현 시 기존 RPC 규칙에 맞추되 다음 경계는 유지한다.

기존에 승인된 기기의 연결과 권한 검사를 사용하며, 새 요청 때문에 인증을 우회하는 파일 접근 경로를 만들지 않는다. 작업은 모두 선택한 호스트에서 실행한다.

1. 모든 변경 요청은 선택한 `hostId`, `bootId`, 대상 ID와 요청 ID를 검증한다. 터미널 대상은 기존 `generation`, 레이아웃 변경은 기존 revision 검증을 유지한다. 재접속한 오래된 응답은 다른 호스트·프로젝트 화면에 적용하지 않는다.
2. `worktrees.open`은 호스트에서 현재 그룹의 기존 터미널을 확인한 뒤 하나만 만든다. 클라이언트가 제안한 최근 터미널 ID는 소속을 검증한다. 동시 클릭·두 기기의 동시 요청도 같은 터미널을 반환한다. 반대로 탭 `+`는 의도적인 추가 생성이다.
3. 생성은 요청 ID로 중복 실행을 막는다. 짧은 저장·예약 구간 뒤 작업 ID를 반환하고, 오래 걸리는 Git 작업은 기존 터미널 mutation queue 밖에서 실행한다. 같은 저장소의 변경은 별도 큐로 순서대로 처리하고 전체 동시 작업 수도 제한한다.
4. Git 완료 후 현재 연결·대상·경로를 다시 검증하고 짧은 queue 구간에서 결과와 레이아웃을 저장한다. 터미널 생성은 워크트리 준비 완료 후 별도 단계다. 호스트 종료 준비에서는 새 Git 작업을 막고 진행 중인 작업의 결과를 안전하게 기록한다.
5. 생성 도중 연결이 끊겨도 재접속하면 작업 ID로 결과를 확인한다. 재시작 시 미완료 작업은 실제 Git 목록과 대조하며, 결과가 불명확한 작업을 재생성하거나 폴더를 자동 삭제하지 않는다.

Git은 셸 문자열 조합 없이 인자 배열로 실행한다. `worktree list --porcelain -z`를 파싱하고, 브랜치를 검증한 뒤 기준 커밋을 고정해 생성한다. 일반 생성에 `--force`, 기존 브랜치를 덮는 `-B`, 자동 stash/reset/clean을 사용하지 않는다. 외부 Git 프로세스와 충돌하면 다시 조회해 원인을 보여준다.

앱 고유의 환경 설정 스크립트·의존성 설치·사용자 명령을 자동 실행하지 않는다. 다만 Git checkout 자체에는 저장소의 hook·filter가 관여할 수 있다. 구현 첫 단계에서 실행 경계를 확인하고, 앱이 호출하는 Git의 hooks는 명령 단위로 비활성화한다. 필터·LFS 동작과 오류를 별도로 검증하며 전역 Git 설정은 변경하지 않는다.

### 저장과 호환

현재 저장 형식은 SQLite `user_version=1`과 `schemaVersion=1`이다. 새 저장 형식은 둘 다 2로 올리고 트랜잭션으로 전환한다. 기존 host ID, 그룹·배치, 터미널 ID·generation, 출력 snapshot은 보존한다. 저장소 배열이 없는 기존 데이터는 빈 배열로 전환하며, 모든 폴더를 임의로 프로젝트로 등록하지 않는다. 구버전 저장소를 잘못 덮어쓰지 않도록 구버전 앱의 재실행도 검증한다.

통신은 기존 방식에 더하는 capability로 구분한다. 새 UI가 구형 호스트에 연결되면 워크트리 기능만 숨기거나 업데이트 안내를 표시한다. 구형 UI의 기존 요청으로 새 메타데이터가 유실되지 않아야 하며, 저장소에 연결된 그룹의 루트를 일반 폴더 편집으로 바꾸는 요청은 명확히 거절한다. 호환을 유지할 수 없는 변경을 발견하면 그때 프로토콜 버전과 업데이트 절차를 함께 설계한다.

현재 설정 내보내기는 그룹 이름·폴더·셸 정보를 다룬다. 첫 구현에서 이를 Git 저장소 복제·워크트리 백업 기능으로 확장하지 않는다. 가져온 그룹은 기존처럼 일반 그룹이며 해당 호스트에서 프로젝트 연결을 다시 확인한다.

## 실패 복구와 삭제

| 상황 | 사용자에게 보이는 결과 |
|---|---|
| 브랜치 중복·이미 사용 중, 대상 폴더 존재 | 해당 입력 바로 아래에 원인을 표시한다. 덮어쓰기나 다른 이름으로의 조용한 변경은 하지 않는다. |
| 워크트리 성공, 셸 실패 또는 터미널 한도 도달 | 워크트리는 남기고 `워크트리는 만들었지만 터미널을 열지 못했습니다`와 재시도 동작을 표시한다. 생성 전체를 다시 실행하지 않는다. |
| Git 성공 뒤 앱 저장 실패·호스트 중단 | 진행 상태를 실제 Git 결과와 대조하고 재연결한다. 사용자 파일을 자동 정리하지 않는다. |
| 폴더가 외부에서 이동·삭제되거나 권한을 잃음 | `폴더 확인 필요`와 경로·새로고침을 표시한다. 기존 출력은 보존하고 다른 경로에서 셸을 대신 열지 않는다. |
| 앱 창만 닫았다 다시 열기 | 기존 실행 중인 셸과 배치를 재연결한다. 워크트리 수만큼 터미널을 새로 만들지 않는다. |
| 호스트·PC 재시작 | 기존 터미널 복원 정책을 유지한다. 이전 명령의 자동 재실행은 하지 않고, 터미널 없이 저장한 워크트리는 그대로 터미널 0개로 복원한다. |

**터미널 닫기, 프로젝트 제거, 워크트리 폴더 삭제를 별개로 처리한다.** 기존 그룹 삭제의 터미널 종료·기록 삭제 확인은 유지하지만 프로젝트 연결 때문에 파일 삭제까지 추가하지 않는다.

워크트리 메뉴의 `워크트리 삭제…`는 첫 구현에서 앱이 만든 연결 워크트리에만 제공한다. 삭제할 폴더·브랜치를 보여주고 브랜치는 남긴다. 원래 작업은 삭제할 수 없다. 외부에서 만든 워크트리는 발견·터미널 열기까지 지원하고 앱에서 폴더를 삭제하지 않는다.

삭제 직전에 전체 호스트의 터미널을 확인한다. 다른 그룹의 연결 터미널, 해당 폴더를 시작 또는 현재 경로로 쓰는 터미널도 함께 검사한다. 참조가 남으면 해당 터미널을 먼저 정리하도록 안내하며 한 번에 강제 종료하지 않는다.

폴더 전체의 수정·추적되지 않은 파일·ignored 파일, 잠금, 하위 모듈, 실제 경로를 검사한다. 첫 구현에서는 보존할 파일이나 판단 불가능한 상태가 있으면 삭제를 중단한다. `.env`나 `node_modules`도 예외로 자동 폐기하지 않는다. 강제 삭제 UI는 포함하지 않는다. 최종 삭제는 재검사 후 일반 `git worktree remove`로 수행한다.

현재 `git.status`는 선택한 cwd 아래의 변경만 보여주고 ignored 파일을 제외하므로 삭제 가능 여부 판정에 재사용하지 않는다. 출력이 잘리거나 조회에 실패한 경우도 깨끗한 상태로 간주하지 않는다. 외부 프로그램까지 완전히 잠글 수는 없으므로 삭제 성공·실패를 실제 Git 결과와 다시 대조한다.

실제 Git 임시 저장소 검사는 [tests/host/git.test.ts](../tests/host/git.test.ts)의 격리 방식에 맞추고, 작업 서비스와 동시 요청 검사를 추가한다. [tests/host/core.test.ts](../tests/host/core.test.ts), [storage.test.ts](../tests/host/storage.test.ts)에는 연결·복원·마이그레이션 영향을 검증한다. UI 검사는 실제 호스트·시험 셸로 두 워크트리의 독립 파일 변경과 PID·cwd를 확인한다.

개발은 `MONGLE_DATA_DIR`를 작업 폴더의 격리 경로로 지정한다. OwnerPipe를 쓰는 데스크톱·패키지 검사는 `MONGLE_E2E_DATA_ROOT`를 `%TEMP%` 아래로 지정한다. 실사용 호스트·인증·Tailscale Serve를 바꾸지 않는다. 타입 검사, 빌드, 관련 회귀를 먼저 수행하고 최종 단계에서 기여 절차의 전체 검사와 실제 앱 시나리오를 확인한다.

구현과 함께 `README.md`, `CHANGELOG.md`의 미배포 변경, `docs/USER-GUIDE.md`, `docs/IMPLEMENTATION-STATUS.md`, `docs/validation/`의 새 검증 기록을 갱신한다. 사용 안내에는 미배포 개발 기능임을 표시해 현재 설치본에서 제공하는 기능과 구분한다.

## 참고 사례와 적용 판단

이번 논의에서 직접 열어 본 Mobbin 화면은 [Front의 사이드바와 메일 상세](https://mobbin.com/explore/screens/3e29dd35-0c1d-4f71-831b-af35c13bf1ec), [Notion의 워크스페이스](https://mobbin.com/explore/screens/cbf7d1f7-7603-405e-ba9e-dc7573bc71e4)다. 계층이 있는 목록, 좁은 내비게이션과 넓은 작업 영역, 과하지 않은 선택 표시를 참고한다. 해당 화면에서 워크트리나 이 생성 폼의 동작을 확인한 것은 아니다.

실제 몽글터미널의 [데스크톱 화면](assets/desktop.png)과 기존 스타일 토큰을 기준으로 색·글꼴·분할·여백을 맞춘다. 이전 생성 시안의 중복 `+`와 전체 작업 공간 전환 방식은 반영하지 않고, 생성 폼에는 터미널 선택 체크박스를 추가한다. 구현 후 실제 앱 조작으로 전환·키보드 초점·모바일 터치를 검증한다.

[GitKraken 공식 터미널 문서](https://help.gitkraken.com/gitkraken-desktop/terminal/)는 워크트리별 독립 터미널과 작업 중 전환을 설명한다. 터미널 수명과 탐색을 구분하는 참고이며, 몽글터미널의 선택적 생성·클릭 시 최초 열기와 완전히 같은 UX라는 근거는 아니다. [Git 공식 worktree 문서](https://git-scm.com/docs/git-worktree)는 공통 저장소에 여러 작업 폴더를 연결하고 목록·생성·삭제를 관리하는 기술 근거다. 이 설계는 그 기능 위에 몽글터미널의 탐색·터미널 규칙을 추가한 제안이다.

## 이번 설계에서 확인한 범위

현재 코드의 그룹·탭·분할 모델, 터미널 생성·이동·복원, SQLite 저장 형식, Git 읽기와 파일 경로 제한을 확인했다. 기존 Git 검사에 연결 워크트리를 읽는 회귀 시나리오가 있으나, 생성·선택적 터미널 열기·삭제 구현의 검증을 대신하지 않는다.

후속 구현으로 프로젝트·워크트리 관리, 선택적 터미널 생성, 탭 표시, 저장·복구·삭제 검사를 추가했다. 실제 Git과 격리된 개발 Electron·ConPTY·승인된 웹 연결을 검증했다. 자동 검사별 결과와 남은 제약은 [검증 기록](validation/worktrees.md)에 기록한다. 설치본 적용·사용자 확인·공개 배포는 수행하지 않았다.
