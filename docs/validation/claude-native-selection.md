# 실제 Windows 앱의 Claude 드래그 검사

2026-10-06, `fix/claude-selection-live`. 구현과 격리 시험 단계이며 새 버전 공개·설치 완료가 아니다.

**최신 상태:** 사용자가 요구한 해결 기준은 고정 입력창과 기존 화면에서의 일반 드래그·스크롤·정확한 복사다. 별도 기록 복사창은 이 요구를 충족하지 못해 철회·제거했다. 일반 렌더링 강제도 사용하지 않는다. 아래는 과거 조사·우회 실험 이력이며, 전체화면 직접 드래그의 해결 완료가 아니다. 오픈소스 터미널·직접 VT 경로와 대조를 진행한다.

## 이전 검증의 한계

0.3.12의 [드래그 검사](terminal-drag-scroll.md)는 일반 xterm 선택과 동일한 전체 프레임의 반복, 시험용 전송·클립보드 경계였다. 실제 Claude 대화와 프로그램 자체 마우스 선택 경로를 검증하지 않았다. 그 결과를 실제 Claude 문제 전체 해결로 해석하면 안 된다.

## 실제 재현 환경

- 공개 ZIP에서 추출한 몽글터미널 0.3.12 Windows 실행 파일을 별도 TEMP 프로필로 실행했다. 기존 설치본·사용자 호스트·터미널은 종료하거나 교체하지 않았다.
- Claude Code 2.1.289의 실제 로그인된 대화에서 도구가 필요 없는 번호·영문·한글 시험 문장을 생성했다. `--safe-mode --tools "" --no-chrome`을 사용했으므로 사용자 플러그인·훅 설정까지 같은 환경은 아니다. 개인 작업 출력이나 인증 데이터는 저장소에 넣지 않았다.
- 실제 창은 Windows 마우스로 조작하고 확인했다. 재현 가능한 느린 드래그는 같은 실행 파일의 Electron `webContents.sendInputEvent`로 150ms 간격 이동을 전달했다. 웹페이지·모의 Claude 응답으로 대체하지 않았다.
- 격리 앱의 정상 IPC 요청과 실제 Windows 클립보드를 비교했다. 수정 후 검사는 이 시험 실행본의 웹 자산을 현재 빌드로 교체하고 화면을 다시 연 결과다. 새 NSIS/ZIP 전체 검증이나 사용자 설치본 업데이트는 아니다.

## 원인과 수정

1. 실제 Claude 응답은 `mouseTrackingMode=any`, SGR 마우스, 대체 화면을 사용했다. 빠른 6줄 선택은 성공했지만 누름 뒤 200ms, 각 이동 사이 150ms를 둔 드래그에서는 `terminal.input`에 누름 한 건만 남고 이동·해제가 사라졌다.
2. 전체 프레임 표시의 `terminal.reset()`이 잠깐 마우스 모드를 NONE으로 바꾼다. xterm은 그때 document의 이동·해제 리스너를 제거한다. 이후 ANY 복원은 다음 누름을 준비할 뿐 진행 중인 제스처의 document 리스너를 다시 붙이지 않는다.
3. 실제 프레임의 마우스 모드는 먼저 반영하고, 화면 복원 중 발생하는 일시적인 프로토콜 알림만 억제한다. 완료·실패 시 알림을 복구하며, 실제 모드 변경은 그대로 반영한다. 마우스 입력 권한·입력 큐·호스트 인증은 바꾸지 않는다.
4. `Shift+드래그`에서는 xterm이 시작 이벤트의 버블링을 중단한다. TerminalPane이 시작을 놓쳐 자동 복사를 실행하지 않았으므로 시작 감지를 캡처 단계로 옮겼다.

## 실제 확인 결과

- 수정 전 빠른 일반 드래그: 응답 완료 후 6줄, 다음 응답 생성 중 기존 6줄 모두 복사됨. 빠른 동작만 검사하면 실패를 놓쳤다.
- 수정 전 느린 일반 드래그: 누름 1건, 이동·해제 0건. 실제 앱에서 선택 범위를 늘리지 못함.
- 수정 후 같은 Claude 세션의 느린 드래그: 누름·이동 12회·해제 전부 전달. LIVE-263~268의 6줄, 359자가 실제 클립보드에 들어옴.
- 수정 후 Shift 선택: 한글 포함 6줄의 모든 글자가 일치(터미널 화면의 앞뒤 패딩 제외), 앱의 클립보드 쓰기 1회, 그 쓰기 문자열과 실제 클립보드는 완전히 일치. CLI 마우스 보고는 전송하지 않음.
- 수정 후 영문 긴 선택: 화면 위 경계에서 2초 유지하며 자동 스크롤. ASCII-001~060의 60줄이 번호·본문·끝 표시까지 전부 원문과 일치. 앱의 클립보드 쓰기는 0회로 프로그램 자체 복사 경로임을 확인.
- **미해결:** 한글을 포함한 긴 응답 123줄 선택에서는 줄 번호는 연속이지만 스크롤로 지나간 일부 줄의 `END-번호` 끝이 빠졌다. 전체 원문 비교는 실패다. 짧은 선택과 영문 긴 선택의 성공으로 이 현상을 덮어 완료 처리하지 않는다. 별도 프로그램·버전 대조 없이는 Claude 자체 결함으로 확정하지 않는다.

## 긴 한글 대화의 우회 경로 검증

시험 대화만 다시 열었을 때 Claude가 시작 배너에서 2.1.291을 표시했다(첫 세션은 2.1.289, 재시작 전 CLI에 업데이트 완료 안내가 있었다). 이 후속 검사를 첫 세션과 동일 버전으로 표현하지 않는다.

[Claude 공식 문서](https://code.claude.com/docs/en/fullscreen#search-and-review-the-conversation)의 `Ctrl+O` → `[`를 실제 창에서 눌렀다. 호스트 화면은 마우스 보고 NONE, 보관 기록 428줄로 전환됐다. 터미널 위쪽 밖으로 드래그하고 8초 유지해 앞선 대화까지 선택했다. LIVE-001~300의 번호·한글·영문·끝 표시 300줄이 원문과 전부 일치했다(화면의 앞뒤 패딩과 첫 줄 응답 표시 기호 제외). 앱 클립보드 쓰기 1회, 쓰기 문자열과 Windows 클립보드 완전 일치, 터미널 입력 0건이었다.

이 경로의 성공은 일반 fullscreen 선택에서 관찰된 줄 끝 누락을 고쳤다는 뜻은 아니다. [Claude 공개 보고 #86954](https://github.com/anthropics/claude-code/issues/86954)에도 스크롤한 선택에서 번갈아 있는 줄의 일부가 빠지는 유사 증상이 있다. 해당 보고는 macOS의 다른 버전으로, 이번 Windows 재현과 동일한 원인인지 확정하지 않았다.

## 자동 검사와 남은 범위

- 타입 검사와 웹·호스트·데스크톱 빌드 통과. 기존 청크 크기 경고는 남아 있다.
- 마우스 알림 회귀 3개와 엔진·기록 복원·입력 큐 관련 검사: 44 통과, 실패·생략 0.
- 기존 브라우저 회귀 파일에 CLI 마우스 DRAG/ANY의 프레임 사이 이동·해제 2개 및 Shift 자동 복사 1개를 추가했다. 로컬 화면 검사는 네이티브 앱으로 진행했다. 첫 CI에서는 DRAG/ANY 두 검사가 통과했고 Shift 복사 내용도 일치했으나, 준비 단계에서 포인터를 옮긴 정상 hover 입력까지 0건으로 기대한 검사가 실패했다. ANY 모드를 켜기 전에 포인터를 배치하도록 검사 준비 순서를 고쳐 드래그 중 입력 0건 검증을 유지했다.
- 실제 응답 생성 중 기존 내용 선택, 출력 완료 후 선택, 느린 드래그, 화면 경계 자동 스크롤, Windows 클립보드를 확인했다. 모든 스트리밍 타이밍·CLI 사용자 설정·버전·원격 웹·모바일을 검증한 것은 아니다. Codex는 이 검사에 포함되지 않았으며 [별도 후속 네이티브 검사](codex-native-selection.md)에 결과를 기록했다.
- 첫 CI(`752ca46`)의 실제 NSIS 교체·복원과 Windows 클립보드·업데이트 연결은 통과했다. 전체 회귀는 421 통과·2 실패(Shift 하위 검사와 이를 포함한 상위 검사)·15 생략이었다. 수정 후 전체 CI는 [PR #44](https://github.com/bokjk/mongle-terminal/pull/44)의 최신 커밋 결과를 따른다. 공개 배포·실사용자 확인은 미수행이다. 긴 한글 fullscreen 복사 누락도 남아 있으므로 전체 드래그 문제 해결 또는 배포 준비 완료로 표시하지 않는다.

## 일반 드래그 호환 기본값 후속 수정

2026-10-06, 같은 시험 대화를 Claude **2.1.291**로 다시 열어 확인했다.

1. 전체화면의 LIVE-001~288은 연속 번호였지만 144줄의 `END-번호`가 `E`까지만 남았다. 몽글은 누름·이동 12회·해제 14건을 전부 전달했고 앱 클립보드 쓰기는 0회였다. 화면 아래 `Jump to bottom` 안내의 위치가 누락된 열과 겹친다. 이는 가림 영역을 포함한 Claude 자체 복사 문제와 일치하는 정황이나, Claude 내부 코드를 수정하거나 원인을 확정한 것은 아니다.
2. 같은 대화를 일반 렌더링으로 다시 열자 마우스 보고 NONE과 일반 터미널 기록 439줄이 확인됐다. 별도 대화 기록 단축키 없이 드래그해 LIVE-001~300 전체 300줄이 원문과 일치했다. 앱 복사 1회, 실제 클립보드 완전 일치, 터미널 입력 0건이었다.
3. 새 셸의 환경을 만드는 `safeShellEnvironment`에 `CLAUDE_CODE_NO_FLICKER=0` 기본값을 추가했다. [Claude 공식 렌더링 선택 규칙](https://code.claude.com/docs/en/fullscreen#fullscreen-by-default)에 따른 일반 렌더링이다. 부모 환경·전역 Claude 설정을 변경하지 않고 이미 지정된 환경 변수 값은 빈 값까지 보존한다. Windows 대소문자 차이로 중복 변수를 만들지 않는다. 기존 셸·실행 중인 Claude는 재시작하지 않는다.
4. 현재 빌드의 실행부와 웹 자산을 시험용 실제 Windows 앱에 적용하고 **새 TEMP 프로필·새 셸**로 다시 실행했다. 셸에서 변수를 따로 설정하지 않고 Claude를 재개했으며 마우스 보고 NONE, 기록 434줄로 시작했다. 새 FIX-001~300 응답을 생성해 터미널 위 경계 밖에서 14초 드래그했다. 번호·한글·영문·끝 표시 300줄 모두 일치, 앱 복사 1회와 Windows 클립보드 완전 일치, 터미널 입력 0건이었다. 선택한 문자열의 앞뒤 화면 패딩과 첫 응답 기호만 제외해 원문을 비교했다.
5. 응답 생성 표시와 토큰 수가 갱신되는 동안 기존 ASCII-031~036을 천천히 선택해 6줄 전체 일치·자동 복사 1회를 확인했다. 모든 응답 스트리밍 타이밍을 망라한 검사는 아니다.
6. Windows 마우스로 FIX-266~271을 직접 드래그해 한글 6줄 원문 일치를 다시 확인했다. 시험 앱·호스트는 정상 종료하고 시험 실행본의 원래 실행부와 웹 진입 파일을 복원했다. 사용자 설치본에는 손대지 않았다.

타입 검사·웹/호스트/데스크톱 빌드, 셸 환경·마우스 회귀 10개를 통과했다. 환경 회귀에는 실제 자식 프로세스의 기본값 수신, 부모 환경 불변, 명시적 0/1/빈 값 보존, Windows 이름 대소문자 처리가 포함된다. 추가로 현재 폴더·작업 복원·터미널 엔진/기록·입력 큐 회귀 56개도 통과했다(관련 총 66개, 실패·생략 0). 전체 CI는 PR 최신 커밋에서 별도로 확인한다.

이 수정은 **몽글의 기본 실행 경로에 대한 호환 조치**다. Claude 전체화면 모드의 자체 복사 결함은 남고, `CLAUDE_CODE_NO_FLICKER=1`로 명시적으로 선택하면 해당 경로를 다시 사용한다. 일반 렌더링은 Claude의 고정 입력창과 내부 마우스 조작 대신 터미널 기록을 사용하므로 화면 동작이 달라진다. WSL·SSH 환경 전달, 모든 CLI 버전·사용자 설정, 사용자 설치본 적용과 새 공개 배포는 이 결과에 포함하지 않는다.

## 전체화면 안내 겹침 대조 검사

2026-10-06, Claude Opus 모델에 코드·기존 증거의 독립 검토를 맡기고 대조 결과를 여러 차례 전달해 해석을 교차 검토했다. 실제 앱 조작과 클립보드 비교는 주 작업자가 수행했다. Opus가 실제 앱을 별도로 시험한 것으로 계산하지 않는다.

같은 합성 시험 대화를 Claude 2.1.291, `--safe-mode --tools "" --no-chrome`, `CLAUDE_CODE_NO_FLICKER=1`로 다시 열었다. 공개 0.3.12 추출 실행 파일에 PR #44 웹 자산을 적용하고 새로운 TEMP 프로필을 사용했다. 느린 드래그는 실제 Electron 창에 누름, 150ms 간격 이동 12회, 경계 유지, 해제를 전달했다. 모든 결과는 실제 Windows 클립보드 문자열이다.

비교 전 각 줄의 앞뒤 화면 공백과 첫 응답 표시 기호만 제외했다. 170열 클립보드에는 앞선 별도 LIVE-031~040 샘플도 포함되어 LIVE 줄을 단순 집계하면 310줄이다. 정확 비교는 **마지막 LIVE-001부터 이어지는 LIVE-300까지**를 대상으로 했다. 각 시험의 마우스 입력은 14건이고 몽글의 클립보드 쓰기는 0회였다. 170열 시험의 추가 입력 1건은 포커스 알림 `ESC[I`로 마우스 입력과 구분했다.

148열 화면에서 `Jump to bottom` 안내는 가로 약 685px부터 시작했고 본문 끝은 약 725px였다. 화면 자체에서도 안내에 가려진 `END-299`가 `E`까지만 보였다. 170열에서는 안내가 약 594px부터, 본문 끝은 약 558px로 겹치지 않았다. 같은 한글 본문을 두 방향·두 너비로 비교한 결과는 **안내가 덮은 화면 칸이 Claude 자체 복사에서 빠진다**는 가설을 강하게 지지한다. 한글 폭 계산만의 문제로 단정할 수 없으며 Claude 내부 소스의 정확한 결함 위치는 확인하지 않았다.

`Ctrl+L`은 선택 강조를 해제했으므로 기존 선택을 재복사하는 해결책으로 확인하지 못했다. [공식 가상 스크롤 비활성 옵션](https://code.claude.com/docs/en/env-vars)을 별도 시험 셸에만 적용해도 누락이 남았다. 이때 상단의 고정된 이전 프롬프트 표시가 사라지고 그 자리에 본문 한 줄이 더 보이는 변화도 관찰했다. 따라서 이 옵션을 제품 기본값이나 복사 해결책으로 추가하지 않는다. `autoScrollEnabled=false`의 세션 한정 설정 경로는 확인하지 못해 시험하지 않았다. `/copy`, 다른 버전·사용자 설정·원격 환경과 Windows Terminal 등 다른 터미널은 이번 대조에 포함하지 않았다.

이번 후속 작업에서는 제품 코드를 추가로 변경하지 않았다. 일반 렌더링 호환 기본값과 사용자가 명시한 값의 보존을 유지한다. 아래 방향 선택과 넓은 창은 시험 조건에서만 성공한 우회이며 안내가 덮은 줄에서 손을 놓으면 여전히 잘릴 수 있다. 정확한 긴 복사에는 앞서 검증한 `Ctrl+O` → `[` 기록 보기 또는 일반 렌더링을 안내한다. 누락된 글자를 몽글에서 추정해 클립보드에 덧붙이지 않는다.

시험 앱과 호스트는 정상 종료했고 추출 시험본의 원래 웹 진입 파일을 복원했다. 실사용 설치본·사용자 터미널·전역 Claude 설정은 변경하지 않았다. [외부 문제 보고 초안](claude-fullscreen-copy-report.md)은 재현 절차만 정리했으며 외부에 제출하지 않았다. 전체화면 근본 수정·새 공개 배포 완료가 아니다.

## 오픈소스 소스 대조와 Computer Use 재검사

2026-10-06. 별도 기록 복사창의 제품 코드·사용 안내·전용 검사를 제거했다. 이 기능은 사용자 요구인 기존 화면의 일반 드래그를 해결하지 못했다. 일반 렌더링을 강제하는 기본값도 제거된 상태를 유지한다. 위의 우회 실험은 조사 이력이며 현재 제품의 해결책이 아니다.

### 소스에서 확인한 차이

- [xterm 6 AttachAddon](https://github.com/xtermjs/xterm.js/blob/6.0.0/addons/addon-attach/src/AttachAddon.ts)은 WebSocket 출력을 기존 터미널의 `write`로 이어 붙인다. [ttyd](https://github.com/tsl0922/ttyd/blob/main/html/src/components/terminal/xterm/index.ts)도 출력 경로와 재연결 초기화를 구분한다. 몽글의 전체 프레임 재구성에서는 매번 `reset()`이 호출된다.
- [Windows Terminal 마우스 입력](https://github.com/microsoft/terminal/blob/main/src/terminal/input/mouseInput.cpp)은 같은 위치의 중복 이동을 거르며 SGR 좌표를 변환한다. 몽글의 좌표가 항상 한 칸 어긋난다는 증거는 찾지 못했다.
- 몽글의 인위적인 reset은 드래그 리스너 외에도 xterm의 직전 이동과 작은 휠 입력의 누적값을 지웠다. 실제 xterm 서비스 대조에서 작은 휠 6회가 연속 경로에서는 `[0,1,0,1,0,1]`, 매번 reset하는 경로에서는 모두 0이었다. 이 상태 보존은 긴 글의 누락과 별도로 수정한다.

### 실제 몽글터미널 조작

격리 TEMP 프로필의 몽글터미널 Windows 실행 파일에 수정 웹 빌드를 적용했다. Claude 2.1.291, 전체화면, 148열·45행, 고정 입력창을 유지했다. Computer Use의 Windows `drag`, `scroll`, `press_key`, `type_text`로 실제 앱을 조작했으며 복사는 실제 Windows 클립보드를 읽어 비교했다. 이 표는 Aside 웹 검사나 Electron 입력 주입 결과가 아니다.

| 실제 조작 | 결과 |
| --- | --- |
| 응답 완료 후 STABLE-046~051 일반 드래그 | 한글·번호·끝 표시 6줄 전부 일치 |
| Claude가 새 응답을 생성하는 동안 기존 STABLE-051~056 일반 드래그 | 6줄 전부 일치 |
| 새 LIVE 300줄 응답 완료 후 아래에서 위로 드래그 | LIVE-263~300의 38줄 전부 일치 |
| 스크롤 후 안내가 겹친 마지막 행까지 위에서 아래로 드래그 | LIVE-262~300의 39줄 중 마지막 줄만 `END-300` 대신 `E`. **실패** |
| 같은 앱에서 사이드바를 접어 안내가 본문을 덮지 않게 한 뒤 같은 방향·같은 39줄 선택 | LIVE-262~300의 번호·한글·영문·끝 표시 39줄 전부 일치 |

300줄 응답을 생성했지만 이번 Computer Use 조작으로 전체 300줄을 복사한 것은 아니다. 도구의 단일 드래그는 누른 채 장시간 대기를 지정하는 기능이 없어, 38~39줄 선택과 경계 스크롤을 확인했다. 앞선 Electron 입력 주입의 장시간 드래그 결과와 구분한다. 너비 변경은 원인을 좁히기 위한 대조 조건이며 사용자에게 제시하는 수정이나 대체 사용법이 아니다.

### 남은 누락의 코드 경로와 판단 한계

Opus가 설치된 Claude 실행 코드에서 선택 문자열 생성 경로를 별도로 검토했다. `Jump to bottom`은 `noSelect` 영역으로 그려지고, `getSelectedText`의 행 수집은 합성 화면에서 이 셀들을 제외한다. 스크롤로 화면 밖으로 나가는 선택 행도 같은 수집 함수를 이용한다. 확인한 버튼 표시 조건에는 드래그 중 숨김이 연결되어 있지 않고, 복사 시 가려지기 전 원문 셀을 복구하는 경로도 찾지 못했다. 실행 파일·전역 설정·인증 정보는 수정하지 않았다.

이 분석과 실제 39줄 실패는 안내가 덮은 셀의 누락 가설을 지지한다. 다만 다른 터미널에서 같은 버전·좌표·이벤트로 직접 대조를 끝내지 못했으므로 몽글의 모든 영향을 배제했다고 주장하지 않는다. Windows Terminal의 UI 조작은 도구에서 차단돼 실기 검사를 완료하지 못했다. 표준 xterm의 직접 VT 비교용 웹 화면은 실행·스크롤까지 확인했지만 사용자 지시에 따라 복사 대조 전에 중단했다. 이 준비 작업을 다른 터미널의 성공 또는 동일 실패 증거로 계산하지 않는다.

요구한 기존 화면의 긴 복사는 아직 미해결이며 공개 배포하지 않는다. 별도 복사창, 일반 렌더링 강제, 누락 글자 추정으로 결과를 보정하지 않는다.

### 입력 상태 보존의 최종 보완과 검사 범위

검토 중 실제 RIS 초기화 직후 같은 마우스 모드로 돌아오면 프레임의 최종 모드만으로 실제 초기화를 구분할 수 없다는 결함을 추가 발견했다. 호스트가 `inputResetGeneration`을 전달하고 클라이언트는 세대 변경·실제 모드/인코딩 변경·resize에서 이전 이동과 휠 잔량을 폐기한다. 동일 세대 재그리기에서만 보존하며 비동기 처리 중 들어온 새 입력을 완료 시 과거 값으로 덮어쓰지 않는다. 필드가 없는 구형 호스트는 기존처럼 프레임마다 캐시를 비운다. 기록 저장은 필드를 유지하되 새 셸의 기록 복원은 과거 초기화 세대를 이어받지 않는다.

최종 타입 검사·전체 빌드 통과. 마우스·엔진·기록 복원·입력 큐·저장 검사 **60개 통과, 실패·생략 0**. 실제 xterm 파서를 Promise로 멈춰 처리 도중 입력을 검사하고 RIS 분할 입력·프레임 병합·구형 프레임·잘못된 세대값·저장과 복원을 포함했다. `release-check`와 diff 검사도 통과했다. 전체 CI·최종 설치 산출물 검증은 이 숫자에 포함하지 않는다.

위 Computer Use 표는 RIS 세대 전달을 추가하기 전, 입력 상태 보존 웹 빌드를 적용한 실제 앱 결과다. 세대 전달까지 포함한 최종 실행부·웹 빌드로 새 격리 앱을 실행하고 Claude 전체화면 시작·148열·45행·ANY/SGR 상태는 확인했다. 그러나 Computer Use의 창 활성화/화면 조회가 `foreground window did not report a process id` 오류를 반환했고 현재 창 목록으로 다시 선택해도 실패했다. 최종 빌드의 직접 조작 재검사는 완료하지 못했으며 앞선 결과로 대체하지 않는다.

시험 앱·호스트를 정상 종료하고 추출 시험본의 원래 웹 진입 파일·실행부를 복원해 SHA-256 일치를 확인했다. 비교용 합성 세션과 웹 서버도 정리했다. 실사용 설치본·사용자 호스트·인증 데이터는 변경하지 않았다.
