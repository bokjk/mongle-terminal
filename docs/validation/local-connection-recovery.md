# 로컬 연결 오류 복구 기록

2026-09-29. 사용자가 현재 컴퓨터의 전용 앱에서 연결 안내를 보고했고, 정확한 오류는 `Owner IPC server authentication failed.`였다. 원격/Tailscale 연결 설정을 요구하는 상황이 아니다. 창과 별도로 실행되는 로컬 터미널 호스트의 인증 단계에서 앱 연결이 중단된 상태였다.

## 확인된 사실

- 실패한 GUI PID 7284는 현재 `release/win-unpacked/MongleTerminal.exe`였고, 선택한 컴퓨터는 `local`이었다. 원격 컴퓨터 등록은 없었다.
- GUI, Explorer, 호스트, helper의 Windows 사용자 SID·세션·무결성 수준이 같았다. GUI가 실행한 client helper의 실제 경로와 데이터 디렉터리도 성공한 진단과 일치했다.
- GUI의 다시 연결 버튼과 선택 파일 저장 시각을 확인했으나 같은 오류가 재현됐다. 다른 Node/Electron 프로세스에서는 동일 helper로 상태 조회가 성공했고, 동시 4개 연결도 성공했다.
- 코드상의 실패 위치는 helper 경로·SID 확인 이후 서버 HMAC 검증이다. 정확한 불일치 원인은 확정하지 못했다. 인증 검증, ACL, secret, 실제 호스트 코드는 변경하지 않았다.

## 복구와 검증

메뉴 정상 종료가 UI Automation COM 오류로 실패해, 연결되지 않은 GUI만 PID·경로·시작 시각을 확인하여 종료했다. 실제 호스트와 셸은 계속 실행시켰다. 같은 배포 EXE를 진단용으로 다시 실행했을 때 `connected`, `owner: true`, 기존 host ID, 패널 3개, 경고 없음, renderer 오류 없음이 확인됐다. 증거는 `test-results/local-connect/actual-app-inspector.json`이다.

진단 GUI 종료를 위한 디버거 명령의 비동기 `require` 참조 오류로 Error 창이 발생했다. 이 오류는 제품의 로컬 인증 오류와 별개인 진단 실수다. 정확한 `--inspect` 프로세스만 정리하고 디버거 없는 일반 앱으로 다시 실행했다. 뒤늦게 끝난 진단 명령의 보조 실행은 단일 인스턴스로 처리됐으며, 최종 일반 GUI PID는 44628, client helper PID는 26644다. 앱 PID가 보유한 디버거 수신 포트가 없음을 확인했다. `test-results/local-connect/normal-launch.json`에 최종 실행 정보를 기록했다.

일반 실행 창 HWnd 2035142에서 UI Automation 읽기 검사를 수행했다. `연결됨` 1개, `연결 끊김`·인증 오류·연결 경고 0개, 터미널 닫기 버튼 3개로 실제 3패널 표시를 확인했다. GUI 명령줄에 디버거 옵션이 없고 직접 자식 client helper 26644가 연결을 유지한다.

`test-results/pane-drag/local-connect-before.json`과 `local-connect-after.json`의 호스트 PID 6400, boot ID, 셸 PID 14060·45092·34256, 세대, 그룹 revision 11과 분할 트리가 동일하다. 실제 셸에 진단 명령을 입력하거나 호스트를 재시작하지 않았다. 사용자 인증 정보와 Tailscale 설정도 유지했다.

**상태는 재시작에 의한 연결 복구이며, 근본 원인의 코드 수정 완료를 의미하지 않는다.** 이후 탐색기 실행에서 같은 증상이 반복되는지 아직 확인하지 못했다. 이 기록을 인증 실패가 영구 해결됐다는 근거로 사용하지 않는다.

## 추가 원인 조사 (2026-09-29)

사용자가 원인 수정 여부를 다시 확인하여 네이티브 인증 코드와 데스크톱 연결 경로를 독립 검토했다. 당시 실패 프로세스가 종료되었고 인증 입력의 차이를 식별할 기록이 없어, 과거 HMAC 불일치의 원인을 정상화 이후 상태만으로 확정할 수 없었다. 인증 검증을 완화하거나 사용자 secret을 교체하지 않았다.

격리된 임시 데이터와 개발 helper로 순차 연결 80회, 8개씩 동시 연결 10회(총 160회)를 실행했다. 인증과 RPC 응답 160/160 성공, 서버 오류 0으로 원래 오류는 재현되지 않았다. 사용자 호스트와 실제 데이터에는 접근하지 않았다. 결과: `test-results/auth-repro/2026-09-29T02-38-05-297Z-c09d4d6f.json`, 재현 코드: `.test-data/auth-repro/stress.ts`.

실제 배포 EXE를 별도 임시 데이터로 실행해 순차 재연결 6회, 12개 동시 요청 2회, GUI 재실행 4회를 확인했다. 폐기 가능한 테스트 데이터의 secret만 의도적으로 변경하면 동일 오류 문구가 발생했고, 원래 값 복원 후 재연결 한 번으로 오류가 사라졌다. 과거 오류가 화면에 계속 남는 현상은 재현하지 못했다. 호스트 boot ID는 유지됐으며 테스트 앱과 호스트는 정리했다. 결과: `test-results/auth-desktop/probe.json`.

이 테스트에서 별도로 발견한 결함은 동시 `selectHost` 요청이 동일한 `desktop-hosts.json.tmp` 파일에 저장하여 `rename`의 `ENOENT`가 발생한다는 것이다(첫 12개 중 8개, 다음 12개 중 9개). 최종 연결은 정상이며 원래 서버 HMAC 오류와의 인과관계는 확인되지 않았다. 두 오류를 같은 원인으로 취급하지 않는다.

이 검사는 정상 연결의 반복 검증 및 의도적인 인증 실패 실험이며 **원래 결함의 회귀 테스트나 근본 원인 수정 증거가 아니다**. 제품 코드 변경 없이 진단 결과만 기록했다.
