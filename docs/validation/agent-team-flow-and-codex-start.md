# AI 팀 흐름과 Codex 첫 메시지, 남은 팀 해제

2026-10-16, Windows x64. **미배포.** 사용자가 0.3.25를 다른 PC와 이 PC에서 시험하며 알려 온 세 문제를 고쳤다. [구성원끼리 메시지](agent-team-relay.md)와 [에이전트에게 메시지 보내기](agent-messages.md)의 후속이다.

## 사용자가 알려 온 문제

1. **Codex 검토가 일을 받지 못함(이 PC):** 팀장·개발은 Claude, 검토는 Codex인 팀에서 개발이 검토에게 보낸 메시지가 팀 대화에 "에이전트가 다시 실행되기를 기다리는 중"으로 남고 검토 터미널에 들어가지 않았다.
2. **검토를 건너뜀(다른 PC):** 같은 구성에서 일 흐름은 `개발 → 검토`였는데 개발이 설계(팀장)에게 보고했고, 검토는 일을 받지 못했다.
3. **팀을 지울 수 없음(다른 PC):** 팀에 연결된 프로젝트(그룹)를 지우자 팀 화면이 열리지 않아, 팀 화면 안에만 있던 **팀 해제…**를 쓸 수 없었다.

## 원인

### Codex는 첫 요청 전에는 시작 훅을 실행하지 않는다

몽글은 Claude·Codex 연동 훅이 "이 셸에서 실행 중"이라고 알려야 메시지를 넣는다. Codex는 `SessionStart` 훅이 그 신호다. 이 PC에서 확인한 사실은 다음과 같다(모두 읽기만 했다).

- 이 PC의 설치본은 0.3.25, Codex CLI는 0.163.0이다. `~/.codex/hooks.json`의 몽글 훅 8개는 `config.toml`의 `[hooks.state]`에 신뢰됨으로 기록되어 있다. 훅 신뢰 확인 미완료는 원인이 아니다.
- 팀 폴더의 검토 실행 설정(`*.mcp.toml`, 역할 지시문)은 `codex -c ... -c ... mcp list`에서 오류 없이 읽혔다.
- PowerShell 입력 기록에는 몽글이 넣은 검토 실행줄(`codex -m 'gpt-6-astra' -c (팀 도구) -c (역할 지시문) -s read-only -a never`) 다음에 `codex`가 한 번 더 있었다. 실행 중인 검토 Codex의 명령줄은 `codex.exe --no-daemon`뿐이었다. 처음 실행된 Codex를 끝내고 다시 띄운 것으로 보인다.

시험용 이름 있는 파이프를 띄우고 몽글 터미널과 같은 환경 변수(셸 토큰, 실행 표식)로 Codex 0.163.0을 실행해, 몽글 훅이 언제 신호를 보내는지 기록했다(`test-results/team-orphan/codex-start-probe.cjs`, 작업 폴더 `.test-data/agent-team-probe/work`).

| 실행 | 결과 |
|---|---|
| `codex --no-daemon`, 요청 없음, 30초 | 입력창(`› Ask Codex to do anything`, `? for shortcuts`)을 그렸고 꺼지지 않음. 훅 신호 0개 |
| 팀 실행 옵션(역할 지시문, 읽기 전용, `-a never`), 요청 없음 | 같음. 꺼지지 않고 신호 0개 |
| 이 PC 팀의 실제 검토 역할 지시문, `gpt-6-astra`, 팀 도구 자리에 시험용 MCP 서버, 요청 없음 | 같음. 꺼지지 않고 신호 0개 |
| `gpt-6-luna`, 입력창이 보이고 1.5초 뒤 "ready" 한 단어 요청(모델 요청 1회) | `SessionStart`(source `startup`) 4.9초, `UserPromptSubmit` 5.6초, `Stop` 12.9초. 아직 불러오는 중에 넣은 요청은 "Queued follow-up inputs"로 대기했다가 처리됨 |

Codex는 첫 요청이 들어와야 대화를 시작하고 그때 `SessionStart`를 실행한다. 그래서 몽글은 첫 요청을 받지 않은 Codex 구성원을 끝까지 "실행 중"으로 보지 않았고, 개발이 보낸 메시지는 보류함에서 기다렸다. 몽글 팀 도구나 실행 옵션 오류는 아니다. 0.3.25 실기 확인은 Claude 구성원 세 명으로만 했기 때문에 이 경우를 보지 못했다.

### 팀장의 "나에게 보고"가 일 흐름을 이김

역할 지시문은 구성원에게 "끝나면 보고 대상에게 보고"라고 알렸지만, 팀장이 일을 맡기며 "끝나면 나에게 보고해"라고 쓰면 그 말을 막는 문구가 없었다. 팀장 지시문에는 일 흐름의 단계를 다 거쳤는지 확인하라는 말도 없었다. 사용자가 다른 PC에서 본 일 흐름은 `개발 → 검토`였으므로 보고 대상 설정은 맞았다.

### 그룹 삭제가 팀을 남김

`groups.delete`는 그룹과 터미널만 지우고 그 그룹의 팀 기록을 남겼다. 팀 화면은 팀의 그룹이 있어야 열리고, **팀 해제…**는 팀 화면 맨 아래 줄 메뉴에만 있었다.

## 동작

- **Codex 첫 메시지:** PowerShell `codex` 감싸기가 대화형 실행(`--no-daemon`을 붙이는 경우)마다 셸 토큰이 붙은 표식 `OSC 777 mongle-codex;<토큰>`을 낸다. 엔진은 표식이 온 순간 화면에 있던 `? for shortcuts` 개수를 기억하고, 그보다 많아졌을 때 훅 신뢰 창과 승인 창이 없으면 한 번만 "입력창 준비"를 알린다. 앞서 실행한 Codex의 글자가 화면에 남아 있어도 준비로 보지 않는다. 실행부는 셸 프롬프트로 돌아오지 않은 PowerShell에서만 이를 받아 보류함을 화면 확인 상태로 연다. 보류함은 이 상태에서 메시지를 **하나만** 보내고, 그 뒤에는 훅(`SessionStart` 등)이 오기 전까지 다시 "준비되기를 기다리는 중"으로 둔다. 시작 직후 1.5초 대기, 입력 중·작업 중·확인 요청·방해 금지 보류, 붙여넣기와 Enter를 나눠 쓰는 방식은 그대로다. 셸 프롬프트 표식이 오면 모두 초기화된다. 감싸기를 거치지 않은 Codex(전체 경로 실행, `codex exec` 등)는 표식이 없어 이전처럼 훅을 기다린다.
- **일 흐름:** 팀장 지시문에 "결과를 누구에게 보내라고는 적지 마세요"와 "사용자에게 끝났다고 알리기 전에 일 흐름의 단계를 모두 거쳤는지 확인하고, 건너뛴 결과는 다음 구성원에게 넘기세요"를 넣었다. 구성원 지시문에는 "맡긴 구성원이 자기에게 보고하라고 해도 결과는 일 흐름대로 보냅니다. 사용자가 직접 다르게 지시했을 때만 그 지시를 따릅니다"를 넣었다. 구성원이 다른 구성원에게 받은 일(팀장 앞으로 온 것 제외) 끝에는 `[몽글 안내] 이 일을 마치면 결과를 send_message로 <다음 차례>에게 보내세요. 일 흐름에 정해진 다음 차례입니다.`가 붙는다. 모델이 이 줄을 베껴 보내면 다음 받는 사람에게는 빠진다. 팀장이 아닌 구성원이 다음 차례가 아닌 사람에게 보내면 도구 답 끝에 다음 차례를 알린다.
- **보내지 못한 메시지:** 구성원이 보낸 메시지가 받는 사람의 터미널이 닫혔거나 CLI가 꺼졌거나 보류함이 가득 차 거절되면 팀 대화에 `전달하지 못함 · 이유`로 남고, 보낸 구성원에게는 사용자에게 알리라고 답한다.
- **팀 해제:** 그룹을 삭제하면 그 그룹의 팀도 `teams.remove`와 같은 정리(기록, 중계 키, 팀 폴더)로 지운다. 사이드바 팀 행마다 `···` 메뉴가 있고, 그룹이 없는 팀은 **프로젝트 삭제됨**으로 표시되며 열 수 없지만 메뉴는 늘 보인다. 실행부를 시작할 때 그룹이 없는 팀을 저절로 지우지는 않는다.

## 남은 제약

- Codex 입력창 판단은 Codex 화면의 `? for shortcuts` 글자에 기댄다. Codex가 이 문구를 바꾸거나 칸이 너무 좁아 그리지 않으면 이전처럼 첫 요청을 기다린다. 그때 팀 대화 입력창 아래 안내가 그 터미널에서 Codex에게 요청을 한 번 보내 달라고 알린다.
- 팀장·구성원이 일 흐름 안내를 따르는지는 모델에 달려 있다.
- 다른 PC에서 그룹을 지워 남은 팀은 이 버전을 설치한 뒤 사이드바 메뉴로 지워야 한다. 자동으로 지우지 않는다.
